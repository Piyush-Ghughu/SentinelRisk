SentinelRisk: Real-Time Payment Authorization & High-Throughput In-Memory Settlement Engine
1. Executive Summary & Core Architectural Problem
1.1 The Domain Problem
In enterprise merchant acquiring, card issuance, and core banking networks (such as Stripe, Adyen, and Visa), transaction authorization operates under strict Service-Level Agreements:

Every authorization request must resolve in under 10 ms at the 99th percentile (p99).

The system must evaluate multi-layer compliance blacklists, enforce dynamic velocity limits to prevent automated card-testing fraud, run behavioral anomaly checks, and deduct balances atomically.

1.2 Why Relational Databases Fail at Scale
Conventional relational database architectures (PostgreSQL, MySQL) fail under high-concurrency payment processing due to:

Row-Level Lock Contention: Executing SELECT ... FOR UPDATE on an account balance serializes concurrent requests, exhausting database connection pools and creating latency spikes exceeding 100 ms.

Double-Spending Under Race Conditions: Decoupled check-then-act application logic (reading a balance via an API, checking if funds exist in Python, and updating the database) allows concurrent requests to drain an account below zero.

Disk I/O Bottlenecks: Logging every transaction attempt directly to disk-backed relational storage creates severe write bottlenecks during traffic spikes.

1.3 The Redis In-Memory Solution
SentinelRisk decouples the critical authorization latency path from persistent disk storage. By executing transaction authorization, rate limiting, sanctions screening, and ledger balance holds entirely within Redis Stack Server (Redis 7+), the system achieves predictable sub-millisecond latencies.

Persistent relational writes (PostgreSQL) are offloaded to asynchronous background ledger services driven by durable Redis Streams, providing deterministic performance and transaction safety.

5. Detailed Implementation of Core Redis Subsystems
5.1 Subsystem 1: Anti-Double-Spend Engine (Redis 7 Lua Functions)
The Architectural Risk
In payment authorization, a double-spend occurs when an account with a $100 balance submits two simultaneous $100 transactions. If both requests read the balance concurrently, both read operations retrieve $100, approve the transaction, and reduce the balance to −$100.

The Resolution Pattern
Redis executes commands in a single-threaded event loop. By wrapping the balance check, available balance deduction, held balance allocation, and ledger hash writes into a single server-side Redis 7 Lua Function, the operation executes atomically. No concurrent operations can execute while the function is evaluating.

-- SentinelRisk Core Financial Ledger Execution Engine
-- Guarantees atomic verification, fund isolation, and zero double-spending

redis.register_function('authorize_hold', function(keys, args)
    local account_key = keys[1]
    local holds_key = keys[2]
    local tx_id = args[1]
    local amount = tonumber(args[2])

    -- Verify parameter integrity
    if not amount or amount <= 0 then
        return redis.error_reply("ERR_INVALID_AMOUNT")
    end

    -- Verify target account existence
    local exists = redis.call('EXISTS', account_key)
    if exists == 0 then
        return redis.error_reply("ERR_ACCOUNT_NOT_FOUND")
    end

    -- Retrieve available balance
    local raw_balance = redis.call('HGET', account_key, 'available_balance')
    local current_balance = tonumber(raw_balance)

    if not current_balance then
        return redis.error_reply("ERR_CORRUPT_BALANCE_STATE")
    end

    -- Strict balance check
    if current_balance < amount then
        return {
            status = "DECLINED",
            code = "INSUFFICIENT_FUNDS",
            current_balance = current_balance,
            attempted_amount = amount
        }
    end

    -- Atomic balance deductions and hold allocations
    redis.call('HINCRBYFLOAT', account_key, 'available_balance', -amount)
    redis.call('HINCRBYFLOAT', account_key, 'held_balance', amount)

    -- Stage hold details in the account holds hash
    local timestamp = redis.call('TIME')[1]
    redis.call('HSET', holds_key, tx_id, string.format('{"amount":%f,"timestamp":%s,"status":"HELD"}', amount, timestamp))

    -- Emit an event directly into the settlement channel
    redis.call('PUBLISH', 'channel:settlements', string.format('{"event":"HOLD_PLACED","tx_id":"%s","amount":%f,"account":"%s"}', tx_id, amount, account_key))

    return {
        status = "AUTHORIZED",
        code = "APPROVED",
        remaining_balance = current_balance - amount,
        hold_amount = amount
    }
end)

redis.register_function('settle_hold', function(keys, args)
    local account_key = keys[1]
    local holds_key = keys[2]
    local tx_id = args[1]

    -- Verify hold existence
    local hold_raw = redis.call('HGET', holds_key, tx_id)
    if not hold_raw then
        return redis.error_reply("ERR_HOLD_NOT_FOUND")
    end

    local hold_data = cjson.decode(hold_raw)
    local amount = tonumber(hold_data["amount"])

    -- Deduct held balance and eliminate hold record
    redis.call('HINCRBYFLOAT', account_key, 'held_balance', -amount)
    redis.call('HDEL', holds_key, tx_id)

    redis.call('PUBLISH', 'channel:settlements', string.format('{"event":"HOLD_SETTLED","tx_id":"%s","amount":%f}', tx_id, amount))

    return {
        status = "SETTLED",
        tx_id = tx_id,
        settled_amount = amount
    }
end)

@router.post("/authorize", response_model=TransactionResponse)
async def authorize_transaction(payload: TransactionRequest):
    redis = await get_redis_client()
    tx_id = f"tx_{uuid.uuid4().hex}"
    start_time = time.perf_counter()

    # Step 1: Write ingestion attempt into Redis Stream
    stream_fields = {
        "tx_id": tx_id,
        "account_id": payload.account_id,
        "amount": str(payload.amount),
        "merchant_id": payload.merchant_id,
        "card_fingerprint": payload.card_fingerprint,
        "currency": payload.currency,
        "timestamp": str(time.time()),
    }

    try:
        # Ingest into stream with automated trimming to keep recent records
        message_id = await redis.xadd(
            name="stream:tx:incoming",
            fields=stream_fields,
            maxlen=500000,
            approximate=True,
        )
    except Exception as e:
        raise HTTPException(
            status_code=500, detail=f"Streaming ingestion error: {str(e)}"
        )

    # Step 2: Trigger inline decision pipeline
    # The API orchestrates parallel checks: Bloom, Velocity, Vector, and Lua Hold
    from app.services.bloom_service import check_aml_sanctions
    from app.services.ledger_service import execute_balance_hold
    from app.services.vector_service import evaluate_behavioral_anomaly
    from app.services.velocity_service import check_sliding_window_rate_limit

    # 1. Sanctions Check
    is_sanctioned = await check_aml_sanctions(redis, payload.card_fingerprint)
    if is_sanctioned:
        execution_time = (time.perf_counter() - start_time) * 1000
        return TransactionResponse(
            tx_id=tx_id,
            status="DECLINED",
            reason="AML_SANCTIONS_MATCH",
            execution_time_ms=execution_time,
        )

    # 2. Sliding Window Velocity Check
    velocity_pass = await check_sliding_window_rate_limit(
        redis, payload.card_fingerprint, limit=5, window_seconds=60
    )
    if not velocity_pass:
        execution_time = (time.perf_counter() - start_time) * 1000
        return TransactionResponse(
            tx_id=tx_id,
            status="DECLINED",
            reason="CARD_VELOCITY_EXCEEDED",
            execution_time_ms=execution_time,
        )

    # 3. Vector Anomaly Check
    anomaly_result = await evaluate_behavioral_anomaly(redis, payload)
    if anomaly_result["is_anomaly"]:
        execution_time = (time.perf_counter() - start_time) * 1000
        return TransactionResponse(
            tx_id=tx_id,
            status="DECLINED",
            reason="BEHAVIORAL_ANOMALY_TRIGGERED",
            execution_time_ms=execution_time,
        )

    # 4. Atomic Balance Hold Execution via Lua Function
    hold_result = await execute_balance_hold(
        redis, payload.account_id, tx_id, payload.amount
    )

    execution_time = (time.perf_counter() - start_time) * 1000

    if hold_result["status"] != "AUTHORIZED":
        return TransactionResponse(
            tx_id=tx_id,
            status="DECLINED",
            reason=hold_result.get("code", "INSUFFICIENT_FUNDS"),
            execution_time_ms=execution_time,
        )

    await redis.publish(
        "channel:telemetry",

    )

        tx_id=tx_id,
        status="AUTHORIZED",
        reason="APPROVED",

import time
import uuid


async def check_sliding_window_rate_limit(
    redis, card_fingerprint: str, limit: int = 5, window_seconds: int = 60
) -> bool:
    """Sliding-window velocity limiter utilizing Redis Sorted Sets (ZSET).

    Removes outdated entries outside the rolling window and guarantees accurate enforcement across boundaries.
    """
    now = time.time()
    clear_before = now - window_seconds
    key = f"velocity:card:{card_fingerprint}"
    unique_member = f"{now}:{uuid.uuid4().hex[:6]}"

    async with redis.pipeline(transaction=True) as pipe:
        # Evict transactions that fall outside the rolling window
        pipe.zremrangebyscore(key, 0, clear_before)
        # Register current transaction timestamp
        pipe.zadd(key, {unique_member: now})
        # Retrieve cardinality of requests within current window
        pipe.zcard(key)
        # Refresh key TTL to bound in-memory lifetime
        pipe.expire(key, window_seconds + 5)

        results = await pipe.execute()
        current_request_count = results[2]

    return current_request_count <= limit

def generate_transaction_embedding(
    amount: float, merchant_id: str
) -> np.ndarray:
    """Generates a normalized 128-dimensional synthetic embedding representing contextual transaction traits."""
    np.random.seed(abs(hash(merchant_id)) % (2**32))
    base = np.random.randn(VECTOR_DIM).astype(np.float32)
    # Project transaction amount into vector space
    base[0] = float(amount) / 1000.0
    norm = np.linalg.norm(base)
    return (base / norm).astype(np.float32)


async def evaluate_behavioral_anomaly(
    redis, payload: TransactionRequest
) -> dict:
    """Executes a hybrid vector search query to find the nearest profile baseline.

    Flags an anomaly if the cosine distance exceeds the risk threshold.
    """
    embedding = generate_transaction_embedding(
        payload.amount, payload.merchant_id
    )
    embedding_bytes = embedding.tobytes()

    # Query the account's historical vector profile baseline
    query = (
        f"(@account_id:{{{payload.account_id}}})=>[KNN 1 @vector $vec AS score]"
    )

    try:
        raw_res = await redis.execute_command(
            "FT.SEARCH",
            INDEX_NAME,
            query,
            "PARAMS",
            "2",
            "vec",
            embedding_bytes,
            "RETURN",
            "2",
            "score",
            "account_id",
            "DIALECT",
            "2",
        )

        if not raw_res or raw_res[0] == 0:
            # Baseline profile missing: pass through to avoid false-positive drop
            return {"is_anomaly": False, "score": 0.0}

        # Distance score returned by HNSW index
        distance_score = float(raw_res[2][1])
        ANOMALY_THRESHOLD = 0.45

        return {
            "is_anomaly": distance_score > ANOMALY_THRESHOLD,
            "score": distance_score,
        }
    except Exception as e:
        # Fallback to standard validation if vector indexing is warming up
        return {"is_anomaly": False, "score": 0.0, "error": str(e)}

import { useEffect, useState, useRef } from 'react';

export interface TelemetryEvent {
  tx_id: string;
  amount: number;
  latency: number;
  status: 'AUTHORIZED' | 'DECLINED';
  timestamp: string;
}

export function useTransactionStream() {
  const [events, setEvents] = useState<TelemetryEvent[]>([]);
  const [connected, setConnected] = useState<boolean>(false);
  const wsRef = useRef<WebSocket | null>(null);

  useEffect(() => {
    const wsUrl = process.env.NEXT_PUBLIC_WS_URL || 'ws://localhost:8000/ws/telemetry';
    const socket = new WebSocket(wsUrl);
    wsRef.current = socket;

    socket.onopen = () => setConnected(true);
    socket.onclose = () => setConnected(false);
    socket.onerror = (err) => console.error("WebSocket Error:", err);

    socket.onmessage = (event) => {
      try {
        const payload: TelemetryEvent = JSON.parse(event.data);
        payload.timestamp = new Date().toLocaleTimeString();
        setEvents((prev) => [payload, ...prev.slice(0, 49)]); // Retain latest 50 events
      } catch (err) {
        console.error("Failed to parse telemetry packet:", err);
      }
    };

    return () => {
      socket.close();
    };
  }, []);

  return { events, connected };
}

8.2 Architectural Interview Defense Questions
Q1: "Why use Redis Streams instead of Apache Kafka?"
Answer: Kafka is optimized for massive, disk-buffered distributed log aggregation with multi-day retention across distributed partitions. SentinelRisk prioritizes sub-millisecond end-to-end authorization latency.

Redis Streams run entirely in memory using Radix trees and listpacks, yielding p99 retrieval latencies below 0.5 ms.

Furthermore, Redis Streams eliminate the operational complexity of ZooKeeper/KRaft clusters, providing consumer groups, message acknowledgment (XACK), and orphaned task recovery (XAUTOCLAIM) out of the box in a unified operational footprint.

Q2: "Why use Lua scripts instead of standard Redis transactions (MULTI/EXEC) or distributed locks (Redlock)?"
Answer: MULTI/EXEC does not allow conditional branching based on intermediate values—it cannot read a balance, compare it against an authorization amount, and conditionally abort inside the transaction.

Redlock introduces multiple network round-trips to acquire, maintain, and release locks, which quickly breaches our 10 ms latency budget.

Redis 7 Lua Functions execute directly within the engine's single-threaded event loop, providing atomic execution, zero network round-trip overhead during decision evaluation, and native replication to read replicas.

Q3: "How do you guarantee persistence and survive server crashes with Redis?"
Answer: We configure a hybrid persistence strategy. SentinelRisk sets:

appendonly yes
appendfsync everysec
maxmemory-policy noeviction
Fsyncing to disk every second limits maximum potential data loss to a single 1-second window while avoiding the heavy disk I/O penalties of appendfsync always.

Setting noeviction ensures that if memory limits are reached, the system returns an explicit error rather than silently evicting active account balances or pending financial holds.
